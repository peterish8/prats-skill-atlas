# Whole-page UX recipes

Choose one recipe using the product's primary action. A premium page needs a coherent route to a useful result, readable uncertainty and recovery from failure. Copy, imagery and motion should explain that route. “Premium” is a craft goal, not a verified conversion or retention effect.

## Creation tool: meadow or citrus

**Page structure:** sparse SiteHeader → single centered MarketingHero with real TaskComposer → alternate entry routes → useful product result/preview → three process/features → concise limits/help → final action. Meadow keeps a narrow center and green light fading to white; citrus uses a broad rounded chassis and a lime object/device stage. Do not combine both hero silhouettes.

**Interaction:** input is controlled; Enter and action button submit the same trimmed value. Block empty input, validate the actual limit, set pending state immediately, and show real progress if the operation has stages. On failure retain input and offer correction/retry. On completion replace or follow the invitation with a useful editable artifact and a truthful saved/unsaved state. Browser-local demos explicitly say “Local preview”; do not imply persistence or AI/backend work.

**Focus:** invalid input remains easy to reach; after a genuine successful transition announce a concise status and put focus where the next task starts if content replacement warrants it. Avoid moving focus for decorative reveals. Repeated submit is guarded at the appropriate host/server boundary; the same-turn component lock does not cover a full request.

## Product marketing: landscape or spectral

**Page structure:** specific proposition/action → recognizable product artifact → three distinct workflow previews → one real usable example → setup/constraints → evidence/FAQ → final action. Landscape gives actual UI a scenic/pastel stage; spectral uses bounded tall poster/art fields. The preview must demonstrate a real capability. A beautiful abstract sculpture cannot explain a product whose strength is an interaction.

**CTA contract:** navigation opens a real section/route via ActionLink; local demo changes actual state; a gated waitlist/contact flow states its meaning. If a feature is planned, say so. Do not invent logos, customer counts, payment volumes, certificates or savings. Feature panels contain short titles, specific actions and the real limitation when it affects the decision.

**Responsive:** copy/action precede art; preserve one readable fragment on phones. A desktop app screenshot scaled to 200 px is ornamental and needs a useful textual account. If horizontal browsing is intended, provide visible previous/next and position feedback. Otherwise stack full cards.

## Institutional explanation: equilibrium or systems

**Page structure:** proposition → main request/access route → process or system relation → exact mechanisms/output → supporting evidence → limits/FAQ → final request. Equilibrium uses a long serif axis and ProcessCard triptych; systems uses asymmetrical copy and a mint schematic. Explain what the service does before using industry terminology.

**Request states:** explicit labeled fields, pending, sent, failed; success tells the next step and a realistic expectation. No silent subscription or external authorization. Keep the critical scope/eligibility/terms visible before the decision. A schematic money/risk icon is illustration, not proof of safety or availability.

## Working workspace: signal or porcelain

**Page structure:** context/navigation → scope/filter controls → primary measure/list → selected detail → task action → confirmation/history. Signal prioritizes data density and exact labels; porcelain uses quiet relief around files/details. Do not place atmospheric art behind a dense table or inflate empty whitespace until the workspace becomes harder to use.

**States:** initial no-records, filter-no-match, loading, loaded, selected, partial, stale, recoverable error, permission denied and completed action. Represent source support, calculations and coverage separately when the product requires it. A failed fetch does not mean a financial claim is false. Progress reports actual stage/count, not a fabricated percentage. Preserve user filters and inputs on retry/reload according to the host contract.

## Integration flow: connected or systems

**Page structure:** concrete integration task → supported named services → requested permission/scope → approved connection action → account/status confirmation → actual test/import result. The decorative map is optional explanatory art. Service availability, account access and authorizations must be real.

**State machine:** disconnected → authorizing → connected, with denied/expired/error alternatives. On error show what can be retried and what permission is missing. On disconnect explain its effect and preserve historical records according to the product contract. Authentication lives in the host, never in a decorative library node.

## First-run guidance: spectral or porcelain

**Page structure:** short welcome → one purposeful choice → concrete artifact/example → a quiet review/summary → real completion. Use OnboardingCard, optional MaterialObject continuity and stable Button position. Host owns step count, answers, Back/Skip and whether steps can be revisited. Do not remount the persistent art or replay milestones on every edit.

**Motion:** logical choice accepted immediately, control confirms, persistent object changes, next content becomes usable while it settles. Reduced motion removes travel but preserves selection/final artifact. Success acknowledges a real event; a visually replayable ending does not repeat the operation. Optional particles are omitted unless they explain a cause/effect and remain bounded.

## State language and accessibility

Use specific status copy: “Loading saved folders”, “No folders match this filter”, “The request was not sent; your text is still here”, “Local preview; not saved”. Generic “Something went wrong” and spinners with no context reduce clarity. A changing message can live in one polite status region; reserve alerts for an actual urgent error. Avoid repeatedly announcing decorative updates.

Ordinary site navigation is a disclosure with native links, not an ARIA application menu. [WAI disclosure navigation example](https://www.w3.org/WAI/ARIA/apg/patterns/disclosure/examples/disclosure-navigation/) supports the distinction. Test keyboard focus, tab/radio controls, native details, dialog exit/focus return and labels. Color always has readable text or shape alongside it. Images carry alt text when they explain a product; decorative original art is hidden from assistive technology.

## Finish the journey

Keep a short decision statement, actual state list and one complete exercised flow. Build/check and visual screenshot evidence are distinct from interaction and real-service proof. The kit cannot authorize production publishing, outreach, payment processing or changing the host's business contracts. Read the host requirements before wiring product behavior.
