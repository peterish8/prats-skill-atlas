# Report Quality and Source Notes

## Required qualities

- A triager should know what is affected, what the attacker must have, exactly how to reproduce it, what happened, and why it matters without guessing.
- Impact must describe the demonstrated result and its realistic security consequence.
- Reproduction must identify the target, roles, parameters, object identifiers, expected behavior, actual behavior, and evidence.
- A suggested fix should be actionable but should not claim an unverified root cause.
- Scope and exclusions should be checked before submission, and the report should avoid unrelated findings in the same record.

## Authoritative reporting sources

- [Bugcrowd Reporting a Bug](https://docs.bugcrowd.com/researchers/reporting-managing-submissions/reporting-a-bug/) — target, technical severity, description, replication steps, impact, evidence, and attachments.
- [Bugcrowd VRT](https://www.bugcrowd.com/products/vulnerability-rating-taxonomy/) — baseline priority classification and why program-specific impact can change the final decision.
- [Google Bug Hunters report guidance](https://bughunters.google.com/learn/improving-your-reports/about-this-section) — clear component identification, attack scenario, and reproduction steps improve triage.
- [Google report-quality framework](https://bughunters.google.com/blog/level-up-your-reports-introducing-our-updated-report-quality-framework) — vulnerability description, preconditions, impact, PoC, target information, output, and responsiveness.
- [HackerOne quality reports](https://docs.hackerone.com/en/articles/8475116-quality-reports) — concise title, detailed steps, expected/actual behavior, impact, and supporting material.
